COMPLETE FACULTY EXPLANATION
============================

"The workflow begins with DTO validation through NestJS ValidationPipe.
AuthService checks duplicate identities, hashes passwords using bcrypt, and
stores users through TypeORM in PostgreSQL.

During login, bcrypt compares the submitted password with the stored hash.
JwtService creates a signed token containing the user's ID, email, and role.

For protected requests, JwtAuthGuard activates Passport's JWT strategy. The
strategy validates the bearer token and places the identity in request.user.
The self-profile endpoints use request.user.id, so the client cannot select
another user's ID. SafeUser responses exclude password hashes.

RolesGuard performs authorization separately from authentication. A valid
agent token receives 403 when it attempts an admin-only operation.

Finally, the password-change flow verifies the current password, stores a new
bcrypt hash, rejects the old password, and accepts the new password."


MEMORY MAP
==========

Registration:

  JSON -> DTO/Pipe -> Controller -> Service -> bcrypt -> Repository -> Database

Login:

  JSON -> DTO/Pipe -> bcrypt.compare -> JwtService -> accessToken

Protected profile:

  Bearer JWT -> JwtAuthGuard -> JwtStrategy -> request.user -> Controller

Authorization:

  request.user.role -> RolesGuard -> allow or 403

Database response:

  User entity -> SafeUser mapping -> password-free JSON

FULL PROJECT STORY TO PRESENT
=============================

"First, four actors register and authenticate with JWT. The administrator
creates a geographic area and approves an MFS provider. The approved provider
onboards an agent, while the administrator onboards a coordinator.

The provider creates physical-cash wallets for the agent and coordinator. The
agent reports a low physical-cash balance and opens a high-urgency liquidity
request. The coordinator discovers that request and submits a matching offer.

After demo funding is seeded, the coordinator executes a wallet transfer.
TypeORM performs the debit and credit atomically, and the Idempotency-Key
prevents duplicate transfers.

The demonstration then covers point balance, notifications, dispute opening
and resolution, provider shortage monitoring, dashboard statistics, role
authorization, DTO validation, PostgreSQL persistence, and Swagger
documentation."


FULL PROJECT LIMITATIONS TO STATE HONESTLY
==========================================

  1. Public role selection currently permits demo admin registration.
     Production must use secure admin seeding.

  2. No API creates the initial coordinator-provider relationship link.

  3. No initial wallet-funding endpoint exists, so the transfer demo needs one
     seeded wallet balance.

  4. Points and notifications are not automatically created by transfers.

  5. Mailer and audit-log modules are not implemented.

  6. Ownership and tenant checks are incomplete in several older endpoints.

Stating limitations is better than claiming behavior that the API does not
currently implement.
